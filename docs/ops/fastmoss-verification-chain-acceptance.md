## 已确认的直接故障

修复前客户端只生成 `fm-sign`，缺少当前前端新增的 **`fm-sig`**。
新签名与路径、排序编码后的 query（含 `_time`、`cnonce`）及 `source` 有关。
复制浏览器 Cookie 不会自动生成这个请求头；更换 nonce 后也不能复用旧签名。

当前页面实际加载的 `29251-88344b67040381e5.js` 中，模块 `961261` 同时生成两种
签名，模块 `877830` 实现 `__SIG__.gen`。实现依据记录于
[接口研究 9.13](../reference/fastmoss-known-interfaces.md#913-2026-09-13-新增请求签名-fm-sig)。

因此，之前“滑块消失但接口未放行”的描述混淆了 UI 状态与新请求再次触发风控。
本次样本中验证码确实通过，浏览器接口也恢复了；旧客户端构造的新请求因签名
不完整又触发风控，继而进入旧恢复循环。不能把八分钟都归结为一次验证码的正常耗时。
这确认了本次直接故障，不表示所有未来的 `MSG_SAFE_0001` 都只有同一个原因。

## 真实对照证据

本节部署前的只读诊断保留登录会话；没有重新登录、清 Cookie、写飞书或写业务事实。
每次浏览器诊断最多一轮、三个滑块尝试；没有提交整批业务请求。

| 对照 | 结果 |
| --- | --- |
| 初次重放工具检查 | HTTP/2 伪头字段不能直接传给 requests；该次没有发出原样重放，结果不作为接口证据 |
| 验证码 `is_ok=true` 后，保留成功请求的 URL 和应用请求头 | 浏览器 `200`，Python 重放 `200`；现有客户端新请求为 `MSG_SAFE_0001` |
| 只更新 `_time`、`cnonce`、`fm-sign`，保留旧 `fm-sig` | 新请求失败，原成功请求随后也失败；立即停止继续比较其他差异 |
| 同时生成对应新 query 的 `fm-sign`、`fm-sig` | 新请求 `200` |
| 仅向现有客户端补充正确的 `fm-sig`，保持其默认 UA、Cookie 构造和其他头不变 | 连续三次 `200`；浏览器原请求及重新加载后的业务请求也均为 `200`；整轮 44.39 秒 |
| 使用修改后的正式纯 Python 实现，无临时补签名 | handler 的浏览器与 HTTP 两阶段均成功；五个不同历史失败达人均返回 `200` 和非空业务数据；整轮 22.77 秒 |

正式实现验收时浏览器会话已有效，没有再次触发验证码，因此该轮的
`captcha_required=false`、`captcha_confirmed=false` 是正确状态。前一轮明确记录了
`is_ok=true`、浏览器成功、HTTP 成功和最终浏览器成功，不以弹层消失代替确认。

这次五对象验收覆盖真实达人基础信息接口；没有执行整批来源发现、事实写入及飞书投影。

## 工作区修复

- 现有 `http_session.py` 为每次实际发送及重试重新生成两种签名；纯 Python 计算，不新增浏览器依赖、服务或模块。
- 移除实际商品视频采集 `list_product_videos` 的旧无签名例外；其他调用方显式 `sign_request=False` 的行为仍保留。没有变更数据库、handler 稳定名称或 payload 外壳。
- `request_verification.py` 分别观察同页验证码确认、同源同对象业务成功及 HTTP 复验。
- 新监控恢复携带 `verification_chain_revision=1`，最多一轮、三个滑块尝试、一次 HTTP 复验。
- 服务端确认和浏览器业务成功后停止拖动；HTTP 失败后不重新清会话、重复滑块。
- Runtime 预算 420 秒，包含 handler 180 秒与既有故障诊断预留 240 秒。
- 三个连续来源恢复失败后走现有取消和子任务收尾流程，保留已完成结果；来源成功打断失败序列。
- 旧 payload 缺少 revision 时保留原恢复语义。

本次提交范围包含原有串行恢复改动及后续双签名、验证链路修复。常驻 worker 已按上述部署记录统一切换；GitHub PR 负责代码审查，本次不合并或发布 release。
